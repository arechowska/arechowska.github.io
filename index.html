Documentation that people and AI can rely on

Banks that use the same software get one set of documentation. Shared text is written once; each bank's differences live in a separate layer.

The same source builds the website, the PDF and the help inside the app, and an AI assistant answers from it. When the assistant can't answer a real user question, that shows what the documentation is missing.

How it works

Most documentation answers “what is this field”. People ask “what do I do next”.

1One source instead of copies

Shared text is written once; each bank's differences live in a layer that says where they apply.

Where it usually breaks: one client's text slips into the shared part, and another bank sees it in search or navigation.

Docs-as-Code at scale →

2Everything is built from it

The website, the PDF and the in-app help come from the same source, checked automatically.

Where it usually breaks: checks catch broken links and style, not meaning. A translated guide can pass every check and still say the wrong thing.

Docs-as-Code at scale →

3AI answers from the same source

An assistant answers users in their own language, with a link to the source and only from their bank's documents.

Where it usually breaks: search, not the model. In the user's own language the assistant finds the wrong section far more often than in the source language.

AI Help →

4Real questions show what is missing

Where the assistant fails on real support tickets, the documentation has a gap, and the fix goes back into the source.

Where it usually breaks: the team's own test questions look great, real tickets score much lower, and a single test run is mostly noise.

About

I'm Ina Arechowska, a documentation architect and DocOps engineer. I work on documentation for enterprise banking software: how it is structured, built and delivered to many client banks, and how an AI assistant can answer from it.

I have a degree in linguistics and computational linguistics, so I look at documentation as data that language models read.

18 years in documentation. Based in Poland.

I studied how language works, and now I watch how machines misread it. That’s where the interesting problems are.
I like work that can be measured. If an assistant is “pretty good”, I want to know on which questions it fails.
